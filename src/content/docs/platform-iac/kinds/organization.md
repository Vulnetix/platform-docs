The organisation's own settings: its display name and its company email domains. One per tenant, named default. A field left out is left as it is. Applying needs an owner or admin. Deleting the document only stops managing these settings: the organisation itself is never deleted, and the settings keep their values.

## Applying this kind

- **Command.** `vulnetix config apply -f <file>`; the CLI line above says from which release. Plan first with [`vulnetix config plan`](/platform-iac/cli/plan/): it shows each object as create, update, delete or no change, with a `planHash` that apply then holds to. Apply writes in one transaction.
- **Manager.** Each object records the manager that applied it (`terraform`, `console` or `gitops:<repo>`). `--prune` deletes only objects its own manager owns. See [The manager](/platform-iac/cli/plan/#the-manager) and the [config engine](/platform-iac/reference/engine/).
- **Status.** Applied, Unchanged or Deleted, with no other status fields. The phases the engine reports are explained under [status phases](/platform-iac/reference/engine/#status-phases).
- **Singleton.** There is one per tenant, and its name is always `default`.

## How apply treats it

- A singleton that merges: a field left out is left as it is.
- Domains are written with the account page's writer on the tenant row. Before the column's migration they read as absent and a write is refused.
- The display name is patched on the Authentik group `org-<slug>` (attribute `display_name`). That write registers an undo that puts the old name back when the apply does not commit.
- Owner or admin only. Delete lets go: the tenant is never deleted.

> [!CAREFUL] Per principal or per tenant
> `companyEmailDomain` is per principal on the account page, while the factory delivery sweep reads the tenant row. The engine writes the tenant row. In a single-person organization they are the same row.
