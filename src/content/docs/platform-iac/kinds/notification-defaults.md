The organisation's default browser push notifications: which events are pushed to a person who has not chosen for themselves. A person's own choices on the notifications page still win. One per tenant, named default. The document replaces the defaults whole, as the console's tenant defaults form does. Deleting it removes the organisation's defaults, so the catalogue defaults apply again.

## Applying this kind

- **Command.** `vulnetix config apply -f <file>`; the CLI line above says from which release. Plan first with [`vulnetix config plan`](/platform-iac/cli/plan/): it shows each object as create, update, delete or no change, with a `planHash` that apply then holds to. Apply writes in one transaction.
- **Manager.** Each object records the manager that applied it (`terraform`, `console` or `gitops:<repo>`). `--prune` deletes only objects its own manager owns. See [The manager](/platform-iac/cli/plan/#the-manager) and the [config engine](/platform-iac/reference/engine/).
- **Status.** Applied, Unchanged or Deleted, with no other status fields. The phases the engine reports are explained under [status phases](/platform-iac/reference/engine/#status-phases).
- **Singleton.** There is one per tenant, and its name is always `default`.

## How apply treats it

- A singleton that replaces: written through the same function as the tenant defaults form, so each change is a factory setting event and an audit entry. Validated like the form.
- Delete removes the setting, so the catalogue defaults apply.
- It does not include the `notify.events` preset, which is a [`FactorySettings`](/platform-iac/kinds/factory-settings/) field. `FactorySettings` must not also manage `notify.push.defaults`, or the two kinds would fight over it.
