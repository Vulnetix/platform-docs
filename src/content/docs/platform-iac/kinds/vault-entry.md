One secret in the tenant's vault: an AI provider key, an environment variable for Pix sandboxes and Belai hosts, or a provider management key, with the grants that say where it may be used. The value is encrypted with KMS before it is stored, is sent once by the client, and is never exported, shown in a plan or returned by any endpoint. No grant means no access, and inside one entry a deny beats an allow. Two active entries that fill the same slot (a provider for provider keys, a variable name for environment variables) may not cover the same subject: a plan that would create such an overlap is refused. Deleting the document revokes the entry: its value is destroyed and it covers nothing, and the vault keeps a stub with its history. Connector secrets (forge tokens, the Wiz client secret) are not VaultEntry documents: they are created through their integration kinds. Automatic rotation is set up in the console and an apply leaves it as it is.

**YAML**

```yaml
# yaml-language-server: $schema=https://github.com/Vulnetix/config-schemas/releases/latest/download/VaultEntry.schema.json
```
```yaml
# An Anthropic key for the AI Firewall and two sandboxes, an environment
# variable for every Belai host but one, and the OpenAI admin key the vault
# rotates provider keys with.
apiVersion: vulnetix.com/v1
kind: VaultEntry
metadata:
  name: anthropic-production
  labels:
    team: platform
  annotations:
    ticket: https://tracker.example.com/SEC-218
spec:
  type: provider_key
  provider: anthropic
  name: Anthropic production
  value: { env: VULNETIX_ANTHROPIC_KEY }
  grants:
    - surface: ai_firewall
      effect: allow
      all: true
    - surface: pix_sandbox
      effect: allow
      ids:
        - 3f1c2a9e-8b4d-4c7a-9e21-5d6f7a8b9c01
        - 7a2e4b6c-1d3f-4e5a-8b7c-9d0e1f2a3b4c

apiVersion: vulnetix.com/v1

  name: npm-token

  type: env
```

## Rules

Conditions the schema enforces beyond each field's own type. `vulnetix config validate` and the engine's plan report a document that breaks one.

| On | Rule |
|---|---|
| `spec` | When `type` is `env`: `name` must be pattern `^[A-Z_][A-Z0-9_]{0,63}$`. Otherwise: `provider` is required and `name` must be pattern `^[A-Za-z0-9][A-Za-z0-9 ._:/@+-]{0,63}$`. |
| `spec` | When `type` is `management`: `grants` must be 0 to 0 items. |
| `spec.grants[]` | Exactly one of these holds: (1) `all` is required and `all` must be `true`; (2) `ids` is required. |

## Applying this kind

- **Command.** `vulnetix config apply -f <file>`; the CLI line above says from which release. Plan first with [`vulnetix config plan`](/platform-iac/cli/plan/): it shows each object as create, update, delete or no change, with a `planHash` that apply then holds to. Apply writes in one transaction, except for the second phase below.
- **Manager.** Each object records the manager that applied it (`terraform`, `console` or `gitops:<repo>`). `--prune` deletes only objects its own manager owns. See [The manager](/platform-iac/cli/plan/#the-manager) and the [config engine](/platform-iac/reference/engine/).
- **Second phase.** This kind is not written inside the apply transaction. The other kinds apply and commit first, then each VaultEntry is written on its own, in the tenant vault. One that fails reports `status.phase: Failed` and a `message`, and nothing is recorded for it. The others stay applied and the apply answers 207. Plan again to see what is left. A single `PUT` from the Terraform provider answers 502 `external_failed` instead.
- **Status.** A failed second-phase write reports phase `Failed` and the entry owns nothing. The phases the engine reports are explained under [status phases](/platform-iac/reference/engine/#status-phases).

## How apply treats it

- The vault lives wholly outside Postgres, so this kind is written in the second phase. After the Postgres transaction commits, each entry is a compare-and-swap of the record inside a small transaction that records its ownership. Its undo puts the entry back (also a compare-and-swap, refused if someone changed it since) when that cannot be recorded.
- A failed entry is reported with phase `Failed` and owns nothing.
- The value is a `valueFrom` secret, required to create, never read back, exported or shown in a plan. The same value again is no change.
- The vault service checks the document, so it is refused for the reasons the vault page refuses it.
- The entry keeps the `metadata.name` it was applied under. An undeclared entry is listed under a name derived from its id, type and provider or variable. The type cannot change.
- Delete revokes the entry, keeping the stub and history. AI firewall and sandbox derives run after the write, in the background, one at a time per tenant.
- Owner only: a token for this kind needs the owner role.
