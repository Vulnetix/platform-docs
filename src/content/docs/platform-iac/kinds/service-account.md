A credential for CI that is not a person. It is named after the organisation, as <organisation>:<metadata.name>, has no email address and cannot sign in. It holds the member role unless spec.role says developer or owner. A member cannot invite people, mint further credentials or change policy. A developer service account can plan, apply and export every kind except Organization, Member, ServiceAccount and VaultEntry, and so is the credential to give Terraform or CI that applies Platform IaC. An owner service account can do everything an owner can. Applying a new ServiceAccount creates it and returns its API key and secret once, in the apply result's status (status.apiKey and status.secret): they are never shown again, by plan, export or the console, so store them as the apply returns them. Applying needs an owner or admin, and only an owner can declare a developer or an owner. Deleting the document deactivates the service account, so its key stops working; it is kept for the audit trail, and its name cannot be used again.

## Applying this kind

- **Command.** `vulnetix config apply -f <file>`; the CLI line above says from which release. Plan first with [`vulnetix config plan`](/platform-iac/cli/plan/): it shows each object as create, update, delete or no change, with a `planHash` that apply then holds to. Apply writes in one transaction.
- **Manager.** Each object records the manager that applied it (`terraform`, `console` or `gitops:<repo>`). `--prune` deletes only objects its own manager owns. See [The manager](/platform-iac/cli/plan/#the-manager) and the [config engine](/platform-iac/reference/engine/).
- **Status.** `status.principal`, `status.apiKey` and `status.secret`, in the apply that creates it and never again. The phases the engine reports are explained under [status phases](/platform-iac/reference/engine/#status-phases).

## How apply treats it

- The spec is empty. The account is always a member.
- Apply returns `status.principal`, `status.apiKey` and `status.secret` once. Plan, export and later applies never show them. Store them as the apply returns them.
- A name that belonged to a deleted account is refused, active or not.
- A create that rolls back deletes the Authentik user it made. A deactivation that rolls back reactivates it.
- Delete deactivates. Secret rotation is not declarable yet: the console's rotate endpoint stays the way to rotate.
- Owner only. A service account with the developer role cannot apply this kind.
