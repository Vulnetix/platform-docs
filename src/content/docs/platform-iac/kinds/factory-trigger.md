Something that starts a Software Factory workflow: a GitHub webhook event, a finding, an issue label, a kanban card move, a firewall sighting, or a person pressing Run. A trigger is a trigger node in the workflow's graph whose id is metadata.name (at most 40 characters), so applying one saves and publishes a new version of the workflow, the same as adding the trigger in the workflow builder; the workflow must be published and must not hold an unpublished draft. A trigger node the workflow already has under that id is adopted. A schedule is a FactorySchedule. Conditions are typed fields: the console takes no expression for a trigger. A trigger is on while its workflow is on. Removing the document removes the node and publishes the workflow again.

## Fields

Paths use dots for nesting and `[]` for the items of a list. **Required** means required whenever the parent object is present. A default is what the server uses when the field is left out.

| Field | Type | Required | Default | Allowed values | Description |
|---|---|---|---|---|---|
| <span id="apiVersion"></span>`apiVersion` | string | yes |  | exactly `vulnetix.com/v1` | The document format version. Every kind in this release is vulnetix.com/v1. |
| <span id="kind"></span>`kind` | string | yes |  | exactly `FactoryTrigger` | Always FactoryTrigger. |
| <span id="metadata"></span>`metadata` | object | yes |  | no other keys |  |
| <span id="metadata-name"></span>`metadata.name` | string | yes |  | pattern `^[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$` | The object's name, unique per kind within a tenant. It is the natural key: plan, apply, export and the Terraform provider all address an object by kind and name. |
| <span id="metadata-org"></span>`metadata.org` | string | no |  | format `uuid` | The tenant (organization UUID) the document belongs to. When set, plan and apply refuse to run against any other tenant. |
| <span id="metadata-labels"></span>`metadata.labels` | object | no |  | map of string to string (length 0 to 256); keys match `^[a-z0-9]([a-z0-9._/-]{0,61}[a-z0-9])?$` | Free key/value labels. Stored with the object, never interpreted by the server. |
| <span id="metadata-annotations"></span>`metadata.annotations` | object | no |  | map of string to string (length 0 to 4096) | Free key/value notes for people and tools, such as a ticket link. |
| <span id="spec"></span>`spec` | object | yes |  | no other keys |  |
| <span id="spec-workflow"></span>`spec.workflow` | string | yes |  | pattern `^[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$` | The metadata.name of a FactoryWorkflow: the workflow the trigger starts. |
| <span id="spec-type"></span>`spec.type` | string | yes |  | `webhook`, `finding`, `label`, `kanban`, `manual`, `firewall` | What starts the workflow. webhook: a GitHub delivery to the App (event, conditions). finding: a new finding (severity). label: a label added to an issue or pull request (label). kanban: a card moved on the board (fromList, toList). firewall: a sighting from a firewall, Guardian or the GitHub risk rules (source and its filters). manual: only a person pressing Run. |
| <span id="spec-title"></span>`spec.title` | string | no |  | length 1 to 200 | The trigger node's title in the builder. Left out, the node is titled with metadata.name. |
| <span id="spec-startAt"></span>`spec.startAt` | array of string | yes |  | 1 to any items; items unique; each item: pattern `^[A-Za-z0-9][A-Za-z0-9_-]{0,39}$` | The ids of the steps in the workflow's graph the trigger leads to: one edge from the trigger to each, in this order. |
| <span id="spec-priority"></span>`spec.priority` | integer | no |  | 1 to 5 | The run's priority, 1 (highest) to 5, when runs wait for capacity. |
| <span id="spec-overlap"></span>`spec.overlap` | string | no |  | `skip_if_running`, `queue`, `cancel_previous` | What happens when a run of the workflow for the same subject is already going. Defaults to skip_if_running. |
| <span id="spec-event"></span>`spec.event` | string | no |  | length 1 to any | webhook: the GitHub event, such as push or pull_request, or one action of it, such as pull_request.opened. firewall: one event of the source, such as package.first_seen (or list several in events). |
| <span id="spec-ref"></span>`spec.ref` | string | no |  | `default`, `tags` | webhook push and release events: default for branch pushes, tags for tag pushes and releases. |
| <span id="spec-conditions"></span>`spec.conditions` | object | no |  | no other keys | webhook: conditions the delivery must meet, all of them. A condition the delivery carries no data for does not match. Globs: * is any run of characters except /, ** includes /, ? is one character; @default is the repository's default branch. |
| <span id="spec-conditions-actions"></span>`spec.conditions.actions` | array of string | no |  | each item: length 1 to any | The event's actions that count, such as opened and synchronize for pull_request. Only when event names no action. |
| <span id="spec-conditions-baseBranch"></span>`spec.conditions.baseBranch` | array of string | no |  | 0 to 30 items; each item: length 1 to 200 | Branch globs the pull request targets, or the pushed branch for a push. |

## Applying this kind

- **Command.** Not yet. The latest CLI, v3.166.0, embeds `config-schemas` v1.3.0, which has no `FactoryTrigger`, so `vulnetix config` refuses the document as an unknown kind before sending it. Use the config API, or Terraform where the kind has a resource, until a CLI release embeds it. Plan first with [`vulnetix config plan`](/platform-iac/cli/plan/): it shows each object as create, update, delete or no change, with a `planHash` that apply then holds to. Apply writes in one transaction.
- **Manager.** Each object records the manager that applied it (`terraform`, `console` or `gitops:<repo>`). `--prune` deletes only objects its own manager owns. See [The manager](/platform-iac/cli/plan/#the-manager) and the [config engine](/platform-iac/reference/engine/).
- **Order.** Applied after [`FactoryWorkflow`](/platform-iac/kinds/factory-workflow/), so a document that refers to one by `metadata.name` can be in the same apply. Deleted before them.
- **Status.** Applied, Unchanged or Deleted, with no other status fields. The phases the engine reports are explained under [status phases](/platform-iac/reference/engine/#status-phases).

## How apply treats it

Written as the Schedules tab writes them: the engine edits the workflow's published graph and publishes it. It is checked by the graph validator's trigger rules and by the typed condition checks. It references its [`FactoryWorkflow`](/platform-iac/kinds/factory-workflow/) by name.

> [!CAREFUL] Conditions are typed, not CEL
> Trigger conditions are typed fields in the document. The CEL `event` context exists in the CEL package, but no released kind has a CEL field in it. See [CEL rule expressions](/platform-iac/reference/cel/).

## Terraform and OpenTofu

The resource is `vulnetix_factory_trigger` in the `vulnetix/vulnetix` provider. Its arguments are the `spec` in snake case, beside `name`, `labels` and `annotations` from `metadata`. The Minimal and Advanced HCL are above. The provider's own reference is [vulnetix_factory_trigger](https://registry.terraform.io/providers/vulnetix/vulnetix/latest/docs/resources/factory_trigger).

Import an object that already exists by its name:

```shell
# Import an existing FactoryTrigger by its name (metadata.name).
terraform import vulnetix_factory_trigger.run_now run-now
```

Install, authentication and how state is read: [Terraform and OpenTofu](/platform-iac/terraform/).

Check a file in an editor with the [schema comment](/platform-iac/schemas/editors/) on its first line, or with the engine's `POST /config/validate`. The latest CLI does not know this kind offline.
