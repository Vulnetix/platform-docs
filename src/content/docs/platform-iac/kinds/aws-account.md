One AWS account the AwsConnection reaches, keyed on its account id within the tenant (two tenants may connect the same account). It takes the connection's connector kind. Deploying puts the Vulnetix pipeline stack in the account through the connection; the per-account advancedNetworking column is written only from AwsConnection.spec.advancedNetworking today. Deleting the document turns the account off rather than forgetting it, because the deployed stack outlives the row and has to stay findable.

## Applying this kind

- **Command.** `vulnetix config apply -f <file>`; the CLI line above says from which release. Plan first with [`vulnetix config plan`](/platform-iac/cli/plan/): it shows each object as create, update, delete or no change, with a `planHash` that apply then holds to. Apply writes in one transaction.
- **Manager.** Each object records the manager that applied it (`terraform`, `console` or `gitops:<repo>`). `--prune` deletes only objects its own manager owns. See [The manager](/platform-iac/cli/plan/#the-manager) and the [config engine](/platform-iac/reference/engine/).
- **Order.** Applied after [`AwsConnection`](/platform-iac/kinds/aws-connection/), so a document that refers to one by `metadata.name` can be in the same apply. Deleted before them.
- **Status.** `stackStatus`, the account's CloudFormation deploy. The phases the engine reports are explained under [status phases](/platform-iac/reference/engine/#status-phases).

## How apply treats it

- Names live in `ConfigManagedObject`. An account nobody declared exports as `aws-<id>-<hash>`.
- `accountId` cannot change under a name, and one account has one name.
- `accountName` is compared only while the account has none, because AWS's alias replaces it.
- `deploy: true` queues the account's stacks when apply creates or changes it. It is never read back.
- Delete stops the sweep and warns that the stacks and findings stay.
