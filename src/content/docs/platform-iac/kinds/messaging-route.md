A messaging workflow: which events go to which messaging connections, filtered how, rendered with which template, and how often. Every event the organisation's producers emit is matched against its routes; a route that takes it renders its template once per target and records each delivery in the console's delivery log. A route whose event types reach a sensitive type (security.*, vault.*, or a sensitive Pix event) is marked sensitive: it may then send to a signed webhook only with allowSensitiveWebhook, and to a GitHub repository only when the repository is private. Each change is recorded as a messaging.route.changed event, as a console edit is. Deleting it stops its deliveries; the delivery log is kept.

## Applying this kind

- **Command.** `vulnetix config apply -f <file>`; the CLI line above says from which release. Plan first with [`vulnetix config plan`](/platform-iac/cli/plan/): it shows each object as create, update, delete or no change, with a `planHash` that apply then holds to. Apply writes in one transaction.
- **Manager.** Each object records the manager that applied it (`terraform`, `console` or `gitops:<repo>`). `--prune` deletes only objects its own manager owns. See [The manager](/platform-iac/cli/plan/#the-manager) and the [config engine](/platform-iac/reference/engine/).
- **Order.** Applied after [`MessagingConnection`](/platform-iac/kinds/messaging-connection/) and [`MessagingTemplate`](/platform-iac/kinds/messaging-template/), so a document that refers to one by `metadata.name` can be in the same apply. Deleted before them.
- **Status.** Applied, Unchanged or Deleted, with no other status fields. The phases the engine reports are explained under [status phases](/platform-iac/reference/engine/#status-phases).

## How apply treats it

Connections are referenced by the `metadata.name` of a [`MessagingConnection`](/platform-iac/kinds/messaging-connection/). Plan blocks a connection the tenant does not have.
