The tenant's AI Firewall policy: which providers and models its agents may use, the guardrails the gateway applies to every request, the hold for review setting, and capability allow and deny lists. One per tenant. This is the document vulnetix ai-firewall apply reads from .vulnetix/ai-firewall.yaml, and every file that command accepts is valid here; metadata, and metadata.name, may be left out.

The same document is the file `.vulnetix/ai-firewall.yaml`, which `vulnetix ai-firewall apply` reconciles and `vulnetix ai-firewall export` writes. The product reference for that file, with the workflow around it, is [Policy file reference](/ai-firewall/reference/policy-file/). This page is the schema reference, and covers what the config engine does with the same document.

      key:
        fromEnv: ANTHROPIC_PROVIDER_KEY
    - slug: acme-vllm
      action: allow
      key:
        fromFile: ~/.config/acme/vllm.key
    - slug: openrouter
      action: deny
    - slug: groq
      action: default
  models:
    - slug: claude-sonnet-4-5
      provider: anthropic
      anyProvider: false
      action: allow
    - slug: qwen3-coder-30b
      provider: acme-vllm
      action: allow
    - slug: gpt-4o-mini
      anyProvider: true
      action: deny
  guardrails:
    - name: block-aws-keys
      baselineId: secrets-aws-access-key
      ruleType: blocked_pattern
      action: block
      pattern: '(?i)AKIA[0-9A-Z]{16}'
      priority: 10
      enabled: true
    - name: cap-conversation
      ruleType: max_messages
      action: block
      pattern: 200
      priority: 50
    - name: redact-pii
      ruleType: pii_redact
      action: redact
      priority: 20
    - name: sealed-blocks
      ruleType: delimiter_integrity
      action: block
      priority: 5
    - name: strip-shell-for-codex
      ruleType: tool_deny
      action: strip
      pattern: Bash
      priority: 30
      when: client == 'codex'
    - name: flag-filesystem-writes
      ruleType: expression
      action: flag
      priority: 40
      enabled: false
      when: "'filesystem' in mcpServers && tools.exists(t, t.startsWith('mcp__filesystem__write'))"
  capabilities:
    approved-mcp:
      family: mcp
      list: allow
      action: block
      patterns: [github, "linear*"]
    banned-clients:
      family: client
      list: deny
      action: block
      priority: 10
      patterns: [unknown]
  holdPolicy:
    holdUnknown: true
    holdTimeoutMinutes: 240
    holdTimeoutAction: deny

## Rules

Conditions the schema enforces beyond each field's own type. `vulnetix config validate` and the engine's plan report a document that breaks one.

| On | Rule |
|---|---|
| `spec.models[]` | Exactly one of these holds: (1) `provider` is required and `anyProvider` must be `false`; (2) `anyProvider` is required, `anyProvider` must be `true` and `provider` is not allowed. |
| `spec.guardrails[]` | When `ruleType` is `expression`: `when` is required, `action` must be `block`, `flag` and `pattern` must be pattern `^\s*$`. |
| `spec.guardrails[]` | When `ruleType` is `max_messages`: `pattern` is required and `pattern` must be >= 1, or pattern `^\s*\+?0*[1-9][0-9]*\s*$`. |
| `spec.guardrails[]` | When `ruleType` is `blocked_pattern`: `pattern` is required and `pattern` must be pattern `\S`. |
| `spec.guardrails[]` | When `ruleType` is `delimiter_integrity`: `action` must be `block`, `flag` and `pattern` must be pattern `^\s*$`. |
| `spec.guardrails[]` | When `ruleType` matches `_(allow\|deny)$`: `pattern` is required, `action` must not be `redact` and `pattern` must be pattern `^\s*[^\^\s](.*[^$\s])?\s*$`. |
| `spec.guardrails[]` | When `action` is `strip`: `ruleType` must be `tool_allow`, `tool_deny`, `mcp_allow`, `mcp_deny`. |
| `spec.capabilities.<key>` | When `family` is one of `skill`, `client`: `action` must be `block`, `flag`. |

## CEL variables

`spec.guardrails[].when` is a CEL expression in the `request` context, returning `bool`. It is evaluated by the AI firewall gateway, for each request. The rule is skipped, named in the decision's skipped list, and the gateway logs it. See [where each expression is evaluated](/platform-iac/reference/cel/#where-each-expression-is-evaluated). The functions, limits and error codes are on [CEL rule expressions](/platform-iac/reference/cel/).

| Variable | Type | Bound | Description |
|---|---|---|---|
| `provider` | `string` | 256 chars | Provider slug, such as `anthropic` or `openai`. |
| `model` | `string` | 256 chars | Model slug as requested. |
| `client` | `string` | 256 chars | Calling client's name, such as `claude-code` or `codex`. |
| `tools` | `list(string)` | 512 items of 256 chars | Tool names the request declares or calls, including flattened MCP tools such as `mcp__github__create_issue`. |
| `mcpServers` | `list(string)` | 128 items of 256 chars | Labels of the remote MCP servers the request wires in. |
| `skills` | `list(string)` | 256 items of 256 chars | Skill names the request offers. |
| `now` | `timestamp` |  | The time of evaluation. Callers may fix it; otherwise it is the clock when Eval runs. |

## Applying this kind

- **Command.** `vulnetix config apply -f <file>`; the CLI line above says from which release. Plan first with [`vulnetix config plan`](/platform-iac/cli/plan/): it shows each object as create, update, delete or no change, with a `planHash` that apply then holds to. Apply writes in one transaction.
- **Manager.** Each object records the manager that applied it (`terraform`, `console` or `gitops:<repo>`). `--prune` deletes only objects its own manager owns. See [The manager](/platform-iac/cli/plan/#the-manager) and the [config engine](/platform-iac/reference/engine/).
- **Order.** Applied after [`AiProvider`](/platform-iac/kinds/ai-provider/), so a document that refers to one by `metadata.name` can be in the same apply. Deleted before them.
- **Status.** Applied, Unchanged or Deleted, with no other status fields. The phases the engine reports are explained under [status phases](/platform-iac/reference/engine/#status-phases).
- **Singleton.** There is one per tenant, and its name is always `default`.

## Two ways to apply it

| | `vulnetix ai-firewall apply` | The config engine |
|---|---|---|
| Reads | `.vulnetix/ai-firewall.yaml`, or `-f <file>` | Documents sent to [`POST /config/plan` and `/config/apply`](/platform-iac/reference/engine/) |
| `metadata.org` | Compared with the authenticated principal | Compared with the tenant, as for every kind |
| A guardrail with no `priority` | Sent as `0` | Written at `100`, the column default the Resolve Platform uses |
| `baselineId` | Not stored | Stored on the guardrail row and exported, so a composed baseline rule round-trips |
| `providers[].key` | Read on the machine running the CLI and stored as the provider key | Not stored; the plan warns. Use [`AiProvider`](/platform-iac/kinds/ai-provider/) `apiKey` for a custom provider's key |
| An `allow` rule whose action is `flag` | Applied | Applied, with a plan warning: it refuses nothing |

Both leave guardrails and model entries the document does not mention alone unless `spec.prune` is `true`, and neither ever prunes a provider entry. Guardrail rows that belong to an [`AiGovernanceList`](/platform-iac/kinds/ai-governance-list/) or to `spec.capabilities` are never touched by `spec.guardrails` or its prune.

## How vulnetix ai-firewall apply behaves

- **Order.** Guardrails, then models, then providers, then keys, then settings, so tightening a policy never passes through a moment where a provider is on and its guardrails are not.
- **Org guard.** If `metadata.org` is set and does not match the authenticated organization, apply refuses. `--force` overrides.
- **Drift.** Guardrails and model entries on the server that the file does not mention are reported and left alone, unless you prune.
- **Dry run.** `--dry-run` prints the plan and changes nothing.
- **Export.** `export` writes the live policy with the baseline pinned off, so applying an export is a no-op. Provider keys are never exported.

> [!WHY] The file works in both places
> Since CLI v3.157.0 `vulnetix config validate`, `plan` and `apply` know this kind, and a file is a Platform IaC document by its content, not its folder. `.vulnetix/ai-firewall.yaml` and a document under `.vulnetix/config` are the same thing: define the policy in one of them. `validate` reads the well-known file since v3.164.0. `plan` and `apply` read the well-known file too since CLI v4.0.0 when no `-f` is given, so `config apply --prune` adopts it. `ai-firewall apply` and `export` are aliases of the config engine for this kind since v4.0.0. See [Which files are Platform IaC documents](/platform-iac/cli/validate/#which-files-are-platform-iac-documents).
