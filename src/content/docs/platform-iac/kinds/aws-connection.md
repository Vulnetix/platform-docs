How Vulnetix reaches the tenant's AWS estate. One per tenant. sso: IAM Identity Center, which can reach every account the operator's session can; the accounts are AwsAccount documents. iamUser: a long-lived access key, for an estate without Identity Center; the key's own account (from sts:GetCallerIdentity, never from the document) is the connected account. An sso connection starts a device authorization that a person approves in the AWS access portal, so its first apply, and any apply after the session expires, cannot finish unattended. Deleting it disconnects AWS; the stacks deployed in each account stay until removed there.

## Applying this kind

- **Command.** `vulnetix config apply -f <file>`; the CLI line above says from which release. Plan first with [`vulnetix config plan`](/platform-iac/cli/plan/): it shows each object as create, update, delete or no change, with a `planHash` that apply then holds to. Apply writes in one transaction.
- **Manager.** Each object records the manager that applied it (`terraform`, `console` or `gitops:<repo>`). `--prune` deletes only objects its own manager owns. See [The manager](/platform-iac/cli/plan/#the-manager) and the [config engine](/platform-iac/reference/engine/).
- **Status.** With `sso`: phase `AwaitingAuthorization` with `authorizationUrl` and `userCode` while the IAM Identity Center sign-in waits, then `Authorized`, or `AuthorizationRequired` when the code expired. The phases the engine reports are explained under [status phases](/platform-iac/reference/engine/#status-phases).
- **Singleton.** There is one per tenant, and its name is always `default`.

## How apply treats it

Every write goes through the AWS drawer's own steps inside the apply transaction. Calls to AWS, KMS and the secrets vault are not transactional: a rolled-back apply can leave an unused OIDC client or a vault version nothing references.

- **`sso`.** Apply starts an IAM Identity Center device authorization when the connection is new or its `startUrl`, `region` or connector changed, and not otherwise. The object's status carries `phase: AwaitingAuthorization`, `authorizationUrl` and `userCode`. The instance that started it polls the device code until the operator approves (`Authorized`) or the code expires (`AuthorizationRequired`, after which the drawer or a new apply starts again). The pending sign-in is held in memory, so another instance reports `AuthorizationRequired` until the token lands.
- **`iamUser`.** Apply proves the key with `sts:GetCallerIdentity` and stores it when the key id is new or a different secret arrives. A new key id without its resolved secret is refused. `secretAccessKey` is write-only, compared by decrypting the stored key, and exported as `{env: ...}`.
- `advancedNetworking` is set on the connection and on every account, as the drawer does.
- Delete removes the row like the drawer's forced disconnect and warns that the CloudFormation stacks stay in each account.

## Terraform and OpenTofu

The resource is `vulnetix_aws_connection` in the `vulnetix/resolve` provider. Its arguments are the `spec` in snake case, beside `name`, `labels` and `annotations` from `metadata`. The Minimal and Advanced HCL are above. The provider's own reference is [vulnetix_aws_connection](https://registry.terraform.io/providers/vulnetix/resolve/latest/docs/resources/aws_connection).

Import an object that already exists by its name (`default`):

```shell
# Import an existing AwsConnection by its name (metadata.name).
terraform import vulnetix_aws_connection.default default
```

A secret is two arguments, never stored in the plan or the state: `secret_access_key_wo` (write-only) and `secret_access_key_wo_version`. Change the version number to send a new value. See [Secrets](/platform-iac/terraform/#secrets).
