A way logs reach Guardian, backed by a Guardian ingest token of the same type. The token is minted on create and shown once, by the apply that creates it; it is never exported or shown in a plan. aws: the token for the vulnetix-siem CloudFormation stack you deploy (IngestToken), which sends VPC flow logs, Route 53 Resolver logs and CloudTrail events by Firehose. cloudflare: Guardian creates Logpush jobs with your Cloudflare API token, which is used for those calls only and never stored. events: the token for POST /v1/ingest/events, used by your own scripts and the Vulnetix runtime sensor. Guardian has no update for a token or a Logpush job, so a changed spec is applied as delete and create: the old token is revoked and a new one minted. Managing sources needs the Guardian manager role.

## Applying this kind

- **Command.** `vulnetix config apply -f <file>`; the CLI line above says from which release. Plan first with [`vulnetix config plan`](/platform-iac/cli/plan/): it shows each object as create, update, delete or no change, with a `planHash` that apply then holds to. Apply writes in one transaction, except for the second phase below.
- **Manager.** Each object records the manager that applied it (`terraform`, `console` or `gitops:<repo>`). `--prune` deletes only objects its own manager owns. See [The manager](/platform-iac/cli/plan/#the-manager) and the [config engine](/platform-iac/reference/engine/).
- **Second phase.** This kind is not written inside the apply transaction. The other kinds apply and commit first, then each LogSource is written on its own, in Guardian. One that fails reports `status.phase: Failed` and a `message`, and nothing is recorded for it. The others stay applied and the apply answers 207. Plan again to see what is left. A single `PUT` from the Terraform provider answers 502 `external_failed` instead.
- **Status.** `status.ingestToken` for an aws or events source, in the apply that creates it and never again. A failed second-phase write reports phase `Failed`. The phases the engine reports are explained under [status phases](/platform-iac/reference/engine/#status-phases).

## How apply treats it

Written in Guardian, in the second phase; see [SIEM kinds](/platform-iac/reference/engine/#siem-kinds-written-in-guardian).

- Only `label` changes in place. Any other change blocks, because Guardian edits Logpush jobs only with the Cloudflare token, which it does not keep.
- Create returns the aws or events ingest token once, as `status.ingestToken` in the apply result, and never again.
- Cloudflare's `apiToken` (`valueFrom`) is used for the create call only and is never compared or exported.
- Delete revokes the ingest token. A cloudflare source's Logpush jobs stay in Cloudflare until removed there, and the plan warns.
- `label` and `zoneIds` are compared only when the document sets them.

## Terraform and OpenTofu

The resource is `vulnetix_log_source` in the `vulnetix/resolve` provider. Its arguments are the `spec` in snake case, beside `name`, `labels` and `annotations` from `metadata`. The Minimal and Advanced HCL are above. The provider's own reference is [vulnetix_log_source](https://registry.terraform.io/providers/vulnetix/resolve/latest/docs/resources/log_source).

Import an object that already exists by its name:

```shell
# Import an existing LogSource by its name (metadata.name).
terraform import vulnetix_log_source.sensor_events sensor-events
```

A secret is two arguments, never stored in the plan or the state: `api_token_wo` (write-only) and `api_token_wo_version`. Change the version number to send a new value. See [Secrets](/platform-iac/terraform/#secrets).

Install, authentication and how state is read: [Terraform and OpenTofu](/platform-iac/terraform/).
