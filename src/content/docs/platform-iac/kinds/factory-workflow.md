A Software Factory workflow: the graph of steps a run walks, from a trigger through scans, decisions, crews, gates and people to its outputs. metadata.name is the workflow's slug (at most 60 characters; slugs that start with sys- belong to the default workflows and cannot be declared). Workflows are versioned: a change to the graph never edits a published version, it saves a new version and, with publish true, publishes it. Triggers and schedules declared as FactoryTrigger and FactorySchedule documents add their own trigger nodes to the graph; those nodes are not part of this document and a graph change keeps them. Removing the document archives the workflow: it is switched off and its triggers removed, and its versions and run history are kept.

  publish: true
  enabled: true
  graph:
    nodes:
      - id: start
        type: trigger
        title: Run by hand
        config:
          kind: manual
        position: { x: 0, y: 0 }
      - id: scan
        type: scan
        title: Scanners
        config:
          source: posture
          scanners: [sca, malscan, secrets]
          failOn: [malware, secrets]
          sbomFormat: cyclonedx-1.6
        githubCalls: { max: 1 }
        onQuotaLow: use_cached
        position: { x: 240, y: 0 }
      - id: patch
        type: crew
        title: Patch and verify
        config:
          crew: belai:security
          mode: goal
          codeTier: smart
          testsPostEnd: goal
          testsOnFail: fix
          maxAttempts: 3
        budget: { tokens: 300000 }
        position: { x: 480, y: 0 }
      - id: gate
        type: gate
        title: Quality gate and tests
        config:
          profile: org_default
          releaseJail: enforce
          onFail: return_to_crew
          checkSource: mirror
          maxGithubCalls: 2
          onQuotaLow: use_cached
        githubCalls: { max: 2 }
        position: { x: 720, y: 0 }
      - id: pr
        type: output
        title: Draft pull request
        config:
          kind: draft_pr
          prState: draft
          reviewers: codeowners
          attach: cdx_slsa
        githubCalls: { max: 2 }
        position: { x: 960, y: 0 }
    edges:
      - { from: start, to: scan }
      - { from: scan, to: patch, label: findings }
      - { from: patch, to: gate, label: branch }
      - { from: gate, to: pr, outcome: pass }
      - { from: gate, to: patch, outcome: fail, loop: true }
    limits:
      runBudgetTokens: 400000
      monthBudgetTokens: 6000000
      concurrency: 2
      githubCallsPerRun: { typical: 4, max: 8 }
      stopTheLineAttempts: 3
      agentCostUsd: 5
      agentFinalizeAt: 0.8
      agentMaxAttempts: 3
      agentMaxContinuations: 2
      agentMaxPasses: 20
      agentMaxWallMinutes: 120
      agentMaxIterations: 80
    scope:
      repos: [acme/payments, acme-labs/*]
      orgs: [acme]

## Applying this kind

- **Command.** `vulnetix config apply -f <file>`; the CLI line above says from which release. Plan first with [`vulnetix config plan`](/platform-iac/cli/plan/): it shows each object as create, update, delete or no change, with a `planHash` that apply then holds to. Apply writes in one transaction.
- **Manager.** Each object records the manager that applied it (`terraform`, `console` or `gitops:<repo>`). `--prune` deletes only objects its own manager owns. See [The manager](/platform-iac/cli/plan/#the-manager) and the [config engine](/platform-iac/reference/engine/).
- **Status.** Applied, Unchanged or Deleted, with no other status fields. The phases the engine reports are explained under [status phases](/platform-iac/reference/engine/#status-phases).

## How apply treats it

- The graph is checked by the console's graph validator.
- A change saves the next version. With `publish: true` it also publishes that version through the console's publish, which reconciles the trigger rows and their schedules in the apply transaction. A published version is never edited.
- The trigger nodes that [`FactoryTrigger`](/platform-iac/kinds/factory-trigger/) and [`FactorySchedule`](/platform-iac/kinds/factory-schedule/) own are left out of the workflow's document, and kept by its graph changes.

### GitOps from a repository

A workflow node, `config-apply`, lets a config repository manage the tenant. Trigger it on a `push` webhook to the repository's default branch.

- It reads every `.yaml` and `.yml` file under the node's `path` (default `.vulnetix/config`) at the pushed commit, through the forge's git API (at most 4 MiB).
- It plans them as manager `gitops:<owner/repo>`, with prune on unless the node sets `prune: false`. The plan is the step's artifact.
- Blocking conditions fail the step with `config_plan_blocked`. No changes: the step succeeds and applies nothing.
- Otherwise, unless `approval: none`, the step asks for a person through the gate node's human approval, carrying the plan hash. Approved, it applies with that hash. A plan that moved since fails with `config_plan_changed` and applies nothing. Rejected or expired, the step fails.
- External objects that fail in the second phase fail the step with their count. Plan again to see what is left.

## Terraform and OpenTofu

The resource is `vulnetix_factory_workflow` in the `vulnetix/resolve` provider. Its arguments are the `spec` in snake case, beside `name`, `labels` and `annotations` from `metadata`. The Minimal and Advanced HCL are above. The provider's own reference is [vulnetix_factory_workflow](https://registry.terraform.io/providers/vulnetix/resolve/latest/docs/resources/factory_workflow).

Import an object that already exists by its name:

```shell
# Import an existing FactoryWorkflow by its name (metadata.name).
terraform import vulnetix_factory_workflow.patch_on_demand patch-on-demand
```

Install, authentication and how state is read: [Terraform and OpenTofu](/platform-iac/terraform/).

## More examples

`examples/FactoryWorkflow/config-apply.yaml` from `Vulnetix/config-schemas`:

```yaml
# A published config-apply step may have an empty config: the phase, path, prune and approval all have defaults.
apiVersion: vulnetix.com/v1
kind: FactoryWorkflow
metadata:
  name: apply-config-on-push
spec:
  graph:
    nodes:
      - id: start
        type: trigger
        title: On a push to the default branch
        config:
          kind: webhook
          event: push
      - id: apply
        type: config-apply
        title: Plan and apply the config
        config: {}
    edges:
      - from: start
        to: apply
```

`examples/FactoryWorkflow/draft-unconfigured.yaml` from `Vulnetix/config-schemas`:

```yaml
# A draft keeps its steps as the console saved them, including steps that are not configured yet: config: {} is accepted while publish is false.
apiVersion: vulnetix.com/v1
kind: FactoryWorkflow
metadata:
  name: triage-sketch
spec:
  publish: false
  graph:
    nodes:
      - id: start
        type: trigger
        title: When a finding arrives
        config: {}
      - id: scan
        type: scan
        title: Scan
        config: {}
    edges:
      - from: start
        to: scan
```

Check a file with `vulnetix config validate -f <file>`. See [Validate documents](/platform-iac/cli/validate/). In an editor, start the file with the [schema comment](/platform-iac/schemas/editors/).
