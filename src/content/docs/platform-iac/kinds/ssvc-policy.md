How the tenant makes its CISA SSVC decision (https://www.cisa.gov/stakeholder-specific-vulnerability-categorization-ssvc) for a finding: Track, Track*, Attend or Act. The decision table is the CISA Coordinator table 2.0.3 and is fixed: four decision points (exploitation, automatable, technical impact, mission and well-being) go in. This document configures how Vulnetix's signals become those four values (CEL over the finding variables, and the repository's criticality for mission and well-being), which table cells the organisation reads differently (mapping), which findings it decides by rule instead (overrides), and what each outcome asks of it (outcomes). A field left out takes the default, which is the policy of a tenant with no document. One per tenant.

```yaml
# yaml-language-server: $schema=https://github.com/Vulnetix/config-schemas/releases/latest/download/SsvcPolicy.schema.json
apiVersion: vulnetix.com/v1
kind: SsvcPolicy
metadata:
  name: default
```
```yaml
  labels:
    team: platform-security
  annotations:
    ticket: https://tracker.example.com/SEC-3120
spec:
  # How Vulnetix's signals become the four decision points. These are the
  # defaults written out, with a stricter automatable test.
  exploitation:
    active: kev || exploitMaturity in ['active', 'weaponized']
    poc: exploitMaturity == 'poc' || exploitCount > 0
  automatable: cvss >= 9.0 || epss >= 0.5
  technicalImpact: cvss >= 9.0 || malicious
  # Mission and well-being, from the repository's criticality.
  missionWellBeing:
    low: low
    medium: medium
    high: high
    critical: high
    unclassified: medium
  # Cells of the CISA table the organisation reads differently.
  mapping:
    - exploitation: [active]
      automatable: [no, yes]
      technicalImpact: [total]
      missionWellBeing: [medium, high]
      outcome: Act
  # Decide by rule, first match wins.
  overrides:
    - name: card data in scope
      when: labels['pci'] == 'in-scope' && severity in ['critical', 'high']
      outcome: Act
    - name: no fix and not reachable
      when: "!reachable && fixAvailability == 'no_fix'"
      outcome: Track
  outcomes:
    track:
      priority: low
      dueDays: 90
    trackStar:
      priority: medium
      dueDays: 60
    attend:
      priority: high
      dueDays: 14
    act:
      priority: immediate
      dueDays: 3
```

## CEL variables

`spec.exploitation.active`, `spec.exploitation.poc`, `spec.automatable`, `spec.technicalImpact` and `spec.overrides[].when` are CEL expressions in the `finding` context, returning `bool`. It is evaluated by the SSVC decision in the Vulnetix site API, on every decision and summary (the summary covers at most 5000 open findings, most severe first, cached for 60 seconds), and by the VDB API for the CLI scan and the remediation plan. The decision point takes its lower value and the decision is still made. An override that fails does not hold. See [where each expression is evaluated](/platform-iac/reference/cel/#where-each-expression-is-evaluated). ## How the decision is made

Vulnetix makes the [CISA SSVC](https://www.cisa.gov/stakeholder-specific-vulnerability-categorization-ssvc) decision, Track, Track*, Attend or Act, for a finding from four decision points. The decision table is the CISA Coordinator table 2.0.3 (CERT/CC) and is fixed. This kind configures how Vulnetix's signals become the four values, which table cells the organization reads differently, which findings it decides by rule, and what each outcome asks of it.

| Decision point | Values | Default |
|---|---|---|
| Exploitation | none, poc, active | active: `kev \|\| exploitMaturity in ['active', 'weaponized']`. poc: `exploitMaturity == 'poc' \|\| exploitCount > 0`. Active wins over poc. |
| Automatable | no, yes | `cvss >= 9.0 \|\| epss >= 0.7` |
| Technical impact | partial, total | total: `cvss >= 9.0 \|\| malicious` |
| Mission and well-being | low, medium, high | The repository's criticality: low, medium, high, and critical (high). A repository with no criticality is medium. |

The expressions are CEL over the `finding` context, so a policy can use any finding variable, including the repository's `labels`, `owner` and `criticality`. The defaults approximate CISA's definitions from the signals Vulnetix holds. Automatable in particular is defined by the kill chain, and the finding context carries no CVSS vector, so the default reads a critical score or a high EPSS as automatable. A tenant that holds better information tightens the expression. `mapping[]` reads cells of the table differently for the whole tenant (the last matching rule wins), `overrides[]` decides by rule after the table and the mapping (the first match wins, and the decision records which rule set it), and `outcomes` sets each outcome's priority and `dueDays` (0 is the standard update cycle).

## How apply treats it

- A singleton, named `default`. The engine stores only what differs from the default policy, so a document that spells a default reads back without it.
- Plan compiles every expression against the `finding` context and refuses unknown values. A stored policy that no longer compiles is not applied: the tenant decides with the default and the routes report a `warning`.
- Delete deletes the row, which returns the tenant to the default policy.
- It needs saas migration `20261228010000_ssvc_policy`. Until it runs, a tenant decides with the default policy, and a write or an apply is refused naming the migration.
- Decisions are made when they are read, from the same facts as the risk ranking, with the repository's asset record. Nothing is stored per finding, so a policy change shows at once. The routes are `GET`, `PUT` and `DELETE /v1/ssvc/policy`, `POST /v1/ssvc/decide` and `GET /v1/ssvc/summary`.

## In the CLI scan and the remediation plan

The VDB API decides with this policy in two more places: the CLI's SCA response (`POST /v2/cli/sca`, the `vulnetix:ssvc` property of each vulnerability) and the remediation plan (`GET /v2/vuln/{id}/remediation-plan`, `response.ssvc`, which takes an optional `?repo=owner/name`). Mission and well-being come from the repository's criticality, and a repository with no asset record is decided as medium.

The policy applies only when the tenant has stored one. With no stored policy, the community credential, a database without the `SsvcPolicy` table, or a stored policy that no longer compiles, both keep the decision they made before policies existed, which is simpler and ignores criticality. A decision made under a policy adds `vulnetix:ssvc:priority`, `:source`, `:exploitation`, `:automatable`, `:technicalImpact`, `:missionWellBeing`, and `:rule` and `:dueDays` when they apply, to a scanned vulnerability, and `policy`, `missionWellBeing`, `source`, `rule` and `dueDays` to the plan's `ssvc` block. The fields that existed keep their meaning.

The resource is `vulnetix_ssvc_policy` in the `vulnetix/resolve` provider. Its arguments are the `spec` in snake case, beside `name`, `labels` and `annotations` from `metadata`.
