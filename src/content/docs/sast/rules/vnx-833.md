## Overview

VNX-833 maps to [CWE-833: Deadlock](https://cwe.mitre.org/data/definitions/833.html). The most common deadlock in application code is a lock-order inversion: one method takes lock A and, while holding it, takes lock B; another method takes B and then A. When two threads run the two methods at once, each holds the lock the other waits for, and neither ever proceeds.

The rule reads nested `synchronized (x)` blocks, instance `synchronized` methods (which hold `this` for their body) and explicit `x.lock()` calls (`ReentrantLock` and similar, held until `x.unlock()`) in each Java file, records every "acquire B while holding A" pair, and reports the inner acquisition of any pair whose reverse also appears in the file.

## What gets flagged

```java
synchronized (accountsLock) {
    synchronized (auditLock) {      // FLAGGED: accountsLock -> auditLock
        audit.record(from, to, amount);
    }
}
// ... elsewhere in the same file
synchronized (auditLock) {
    synchronized (accountsLock) {   // FLAGGED: auditLock -> accountsLock
        e.apply();
    }
}
```

## What is not flagged

- Nested locks always taken in the same order.
- Locks taken one after the other (released before the next is acquired).
- `static synchronized` methods, and an inner lock taken inside a task handed to another thread (`executor.submit(() -> { ... })`, `new Thread(...)`, a `TimerTask`).
- Inversions whose two halves are in different files, and the pattern in comments or string literals.

## Remediation

Define one global order for the locks and acquire them in that order everywhere, for example by ordering on a stable key (`account.id`) before nesting. Where possible, hold one lock at a time, or use `tryLock` with a timeout and back off.
