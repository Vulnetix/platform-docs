## Overview

VNX-263 maps to [CWE-263: Password Aging with Long Expiration](https://cwe.mitre.org/data/definitions/263.html). It reports a password maximum age set to more than 180 days where the value is configured, and prints the configured number of days.

## Why this matters

The maximum age bounds how long a stolen password keeps working when nobody notices the theft. At a year or more, that bound is close to meaningless: a password captured by phishing, a keylogger or a breach of another site stays valid for most of that time. If the organisation has deliberately moved away from scheduled expiry, the long value should be replaced by the controls that make that safe, not left as a pretence of aging.

## What gets flagged

```hcl
resource "aws_iam_account_password_policy" "org" {
  max_password_age = 365
}
```

```python
iam.update_account_password_policy(MinimumPasswordLength=14, MaxPasswordAge=730)
PASSWORD_EXPIRY_DAYS = 365
PASSWORD_MAX_AGE = timedelta(days=500)
```

```java
UpdateAccountPasswordPolicyRequest.builder().maxPasswordAge(1095).build();
public static final Duration PASSWORD_LIFETIME = Duration.ofDays(1000);
```

```shell
PASS_MAX_DAYS	365
chage -M 720 deploy
```

```powershell
Set-ADDefaultDomainPasswordPolicy -Identity corp.example.com -MaxPasswordAge 365.00:00:00
net accounts /maxpwage:999
```

Not flagged: 180 days or fewer; 0, 99999 or -1, which switch aging off and are reported by [VNX-262](/sast/rules/vnx-262/); other durations (sessions, tokens, certificates, password-reset links); comparisons such as `user.passwordAgeDays > 365`; and the settings in comments or string literals.

## Remediation

1. Set the maximum age to the period your policy requires (for example 90 days under the CIS AWS benchmark).
2. If you follow NIST SP 800-63B and do not expire passwords on a schedule, remove the long value and enforce MFA, breached-password screening and forced rotation on evidence of compromise instead.
