## Overview

VNX-708 maps to [CWE-708: Incorrect Ownership Assignment](https://cwe.mitre.org/data/definitions/708.html). It reports a `chown()`, `lchown()`, `fchown()` or `fchownat()` call whose path, uid or gid argument comes from `argv[...]`, `optarg` or `getenv()`/`secure_getenv()`. The value can be used in the call itself, assigned to a variable up to 20 lines above (`atoi(argv[2])`, `strtoul(optarg, ...)`), or passed through one more assignment (`getpwnam(name)` and then `pw->pw_uid`). The rule reads a call that spans several lines up to three lines past its first line.

## Why this matters

When the caller chooses the owner, a file can end up owned by an account outside the program's control sphere. In a setuid or root helper it is worse: the caller can pick an arbitrary path and take ownership of it.

## What gets flagged

```c
uid_t uid = (uid_t)atoi(argv[2]);
gid_t gid = (gid_t)atoi(argv[3]);
if (chown(argv[1], uid, gid) != 0)      // FLAGGED

struct passwd *pw = getpwnam(user);     // user = optarg
return fchown(fd, pw->pw_uid, pw->pw_gid);   // FLAGGED
```

The rule does not report owners that are constants, `getuid()`/`getgid()`, or values copied from `stat()` of another file. It also skips `ops->chown(...)` style function pointers, test code, comments and string literals. It does not follow flows through other functions or files.

## Remediation

1. Take the owner from the program's own trusted configuration, not from the caller.
2. If a user must be named, check the name against an allow-list, and refuse root and system accounts.
3. In a privileged program, open the target with `O_NOFOLLOW` and use `fchown()` on the descriptor once you have checked the path.
