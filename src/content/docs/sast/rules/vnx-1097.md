## Overview

VNX-1097 maps to [CWE-1097: Persistent Storable Data Element without Associated Comparison Control Element](https://cwe.mitre.org/data/definitions/1097.html). It reports a class whose comparison controls are incomplete: the class can be ordered, but equality was never defined to agree with that order.

## Why This Matters

Sorted structures (`TreeSet`, `TreeMap`, `bisect`, sorted de-duplication) treat two objects that compare as 0 as the same element. `==`, `HashSet` and `dict` keep using identity. The same pair of objects is then one entry in one collection and two in another, so lookups, de-duplication and stored copies disagree depending on which structure holds them. `functools.total_ordering` documents that the class must still supply `__eq__`.

Not reported: classes that also define equality, Java records and enums, Kotlin data classes, Python dataclasses and attrs classes, classes that extend another class (equality may be inherited), interfaces, and comments. The pairing of `equals()` with `hashCode()` is reported by [VNX-581](/sast/rules/vnx-581/).

## What Gets Flagged

```java
public final class Version implements Comparable<Version> {
    @Override
    public int compareTo(Version other) {          // FLAGGED: no equals(Object)
        return Integer.compare(major, other.major);
    }
}
```

```python
@functools.total_ordering
class Money:
    def __lt__(self, other):                       # FLAGGED: no __eq__
        return self.cents < other.cents
```

## Remediation

1. Define `equals` (and `hashCode`) or `__eq__` (and `__hash__`) over the same fields the ordering compares.
2. In Kotlin or Python, a data class or `@dataclass(order=True)` generates both consistently.
3. For a confirmed false positive, add a `vulnetix-ignore: VNX-1097` comment on the line.
