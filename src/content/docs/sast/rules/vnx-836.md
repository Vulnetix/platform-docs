## Overview

VNX-836 maps to [CWE-836: Use of Password Hash Instead of Password for Authentication](https://cwe.mitre.org/data/definitions/836.html). When a login endpoint accepts a hash from the client and compares it with the stored hash, the hash *is* the password. Anyone who reads the user table (a SQL injection, a leaked backup) can log in as every user without cracking anything.

The rule reports a comparison (`==`, `!=`, `===`, `.equals()`, `compare_digest()`, `MessageDigest.isEqual()`, `crypto.timingSafeEqual()`) between a stored-hash field or getter (`password_hash`, `passwordHash`, `hashed_password`, `pwd_hash`, `getPasswordHash()`) and a request value: `request.form`/`args`/`json`/`POST`/`GET`, `request.getParameter`/`getHeader`, `req.body`/`query`/`params`/`headers`, a variable assigned from one within the ten lines above, or a Spring `@RequestParam`/`@RequestHeader` String parameter.

## What gets flagged

```python
if user is None or user.password_hash != request.form["password_hash"]:   # FLAGGED
    abort(401)
```

```javascript
if (!user || user.passwordHash !== req.body.passwordHash) {   // FLAGGED
  return res.status(401).end();
}
```

```java
if (user.getPasswordHash().equals(request.getParameter("hash"))) {   // FLAGGED
```

## What is not flagged

- The request password hashed on the server before the comparison (`hashlib`, `pbkdf2_hmac`, `bcrypt`, `hash_password()` and similar).
- `bcrypt.compare(req.body.password, user.passwordHash)`, `check_password_hash(...)` and other verify functions.
- Comparisons of two stored hashes, and the pattern in comments or string literals.

## Remediation

Accept the password itself over TLS and verify it on the server with a password hashing function (bcrypt, scrypt, Argon2, PBKDF2) and its verify call. If the client must not send the password, use a challenge-response or token protocol rather than a static hash.
