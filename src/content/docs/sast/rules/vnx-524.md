## Overview

VNX-524 maps to [CWE-524: Use of Cache Containing Sensitive Information](https://cwe.mitre.org/data/definitions/524.html). A password in a cache outlives the request, is shared with everything else that can read the cache (another tenant, a debug endpoint, a Redis or memcached dump), and a memoised credential check keeps succeeding after the password is changed. The rule reports:

- Python `functools.lru_cache`/`cache`, cachetools `@cached` and `@memoize` on a function with a password parameter;
- Java Spring `@Cacheable` on a method with a password parameter;
- lodash/memoizee `memoize()` of a function with a password parameter;
- a cache write (`cache`, `redis`, `memcache`, `lru` receivers: `set`, `setex`, `add`, `put`, `hset`, `set_many`) whose key or value is a password variable or a request's password field.

## What gets flagged

```python
@functools.lru_cache(maxsize=1024)               # FLAGGED
def check_credentials(username: str, password: str) -> bool:
    return ldap_bind(username, password)

cache.set(f"signup:{key}", password, timeout=600)  # FLAGGED
```

```java
@Cacheable("logins")                             // FLAGGED
public User login(String username, String password) { ... }
```

## What is not flagged

Password hashes and digests (`password_hash`, `hashedPassword`), tokens and other values, flags and messages about passwords (`password_reset_sent`, `passwordChangedAt`), cached functions without a password parameter, comments and test code. Model attributes such as `user.password` are not followed, since they usually hold the hash.

## Remediation

1. Never cache credential checks or the passwords themselves.
2. When a multi-step flow needs state, cache an opaque reference or a hash, never the password.
3. If authentication results must be cached, key them by a session identifier and invalidate them on password change.
