## Overview

VNX-409 maps to [CWE-409: Improper Handling of Highly Compressed Data (Data Amplification)](https://cwe.mitre.org/data/definitions/409.html). The rule reports decompression whose output size is not bounded, so a small compressed input (a zip or gzip bomb) expands until memory or disk runs out.

## Why this matters

Compression ratios of 1000:1 are easy to build, and nested archives reach far more. A server that decompresses an upload or a request body without capping the output lets one small request exhaust memory or fill the disk.

## What gets flagged

```python
with zipfile.ZipFile(upload) as zf:
    zf.extractall(UPLOAD_DIR)                 # FLAGGED: no file_size check in the file

payload = request.get_data()
raw = gzip.decompress(payload)                # FLAGGED: request body, no output limit

shutil.unpack_archive(saved_path, plugin_dir) # FLAGGED
```

```javascript
const body = zlib.gunzipSync(req.body);              // FLAGGED: no maxOutputLength
req.pipe(zlib.createGunzip()).pipe(out);             // FLAGGED
zip.extractAllTo(dir, true);                         // FLAGGED (adm-zip)
```

Not flagged: `zlib.gunzipSync(buf, { maxOutputLength: 1 << 20 })`, `zlib.decompressobj().decompress(data, MAX)`, an archive whose members' `file_size` is summed before extraction, Python decompression of local or constant data, compression calls (`gzipSync`, `createGzip`), test files, comments and strings.

## Remediation

1. Node: pass `{ maxOutputLength: <limit> }` to every zlib convenience method; count bytes in a Transform for streams.
2. Python: sum `info.file_size` over `infolist()` and reject archives over a limit; use `zlib.decompressobj().decompress(data, max_length)` for streams.
3. For confirmed false positives, add a `# vulnetix-ignore: VNX-409` comment on the line.
