## Overview

A credential check with a hidden way in: the real verification (`check_password`, `password_verify`, a bcrypt or argon compare, `authenticate`, `matches`, `verify`, `checkpw`) is OR-ed on the same condition line with a comparison of the supplied password, PIN, token, secret or API key against a hard-coded literal, so a master password logs in as anyone. The rule also reports a username and a password both compared to literals in one AND-ed condition: a hidden built-in account.

## Why This Matters

Anyone who reads the source, a leaked copy or the compiled binary learns a credential that works for every account, and it never appears in the user store, so audits of accounts do not find it.

## What Gets Flagged

```python
if check_password_hash(user.pw_hash, password) or password == "Spring2019!":
    login_user(user)

if username == "support" and password == "s3rv1ce-desk":
    return grant_admin()
```

```java
if (encoder.matches(password, user.getHash()) || password.equals("Adm1nOverride")) {
```

```javascript
if (await bcrypt.compare(req.body.password, user.hash) || req.body.password === 'qa-override') {
```

Not flagged: comparisons with empty or two-character literals, `!=` tests, password-policy checks that are not OR-ed with a verifier, field-type comparisons (`type === 'password'`), test files, comments and strings. A hidden request parameter that grants access is VNX-656; hard-coded credentials in general are VNX-798.

## Remediation

Remove the literal comparison. Support and recovery access belongs in real, audited accounts with their own credentials, or in a break-glass procedure that is logged and rotated.
