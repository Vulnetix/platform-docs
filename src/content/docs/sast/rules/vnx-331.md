## Overview

VNX-331 maps to [CWE-331: Insufficient Entropy](https://cwe.mitre.org/data/definitions/331.html). It reports a secret generated with less than 128 bits of randomness, when the same line names it as a token, secret, key, password, salt, session id, CSRF, API key, reset or invite value.

## Why This Matters

A good generator does not help if it is asked for four bytes: 32 bits can be enumerated, and a short salt or key loses most of its protection. `uuid1()` is built from a timestamp and the host's MAC address, not randomness.

## What Gets Flagged

```python
# FLAGGED
api_key = secrets.token_hex(4)
salt = os.urandom(4)
token = str(uuid.uuid1())
invite_token = uuid.uuid4().hex[:8]
```

```javascript
// FLAGGED
const token = crypto.randomBytes(4).toString('hex');
```

```java
// FLAGGED: an 8-byte salt filled by nextBytes()
byte[] salt = new byte[8];
```

## What Is Not Flagged

- 16 bytes or more, and the `secrets` defaults (32 bytes).
- Short random values with no security name (file names, colours, trace ids).
- Nonces and IVs, whose size is set by the cipher (a 12-byte GCM nonce is correct).
- `uuid4()` in full, comments and test files.

Non-cryptographic generators are reported by [VNX-PY-005](/sast/rules/vnx-py-005/) and [VNX-JAVA-016](/sast/rules/vnx-java-016/); small numeric ranges by [VNX-334](/sast/rules/vnx-334/).

## Remediation

Use at least 16 random bytes from a CSPRNG for every secret: `secrets.token_urlsafe(32)`, `crypto.randomBytes(32)`, or a 16+ byte array filled by `SecureRandom.nextBytes`.
