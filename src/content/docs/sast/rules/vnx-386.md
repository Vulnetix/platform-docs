## Overview

VNX-386 maps to [CWE-386: Symbolic Name not Mapping to Correct Object](https://cwe.mitre.org/data/definitions/386.html). It reports `Class.forName()` and `ClassLoader.loadClass()` whose class-name argument is built by concatenation or `String.format`/`formatted` with a variable part (also across a line break), or is a variable assigned in the 15 lines above from such an expression or from request data (`getParameter`, `getHeader`, `getQueryString`, `getPathInfo`, `getCookies`, `readLine`).

Not reported: literal class names, ALL_CAPS constants, `X.class.getName()`, concatenations of literals only, a lookup preceded in the 10 lines above by an allow-list check of the variable (`ALLOWED.contains(kind)`, a validator, `matches()`), map-based registries of `Class` objects, comments and string literals. Request-supplied class names are also reported by VNX-470 (unsafe reflection).

## Why this matters

A class name built from data can resolve to a class other than the one intended: any class on the classpath whose name the input can spell, including ones with dangerous constructors or static initialisers.

## What gets flagged

```java
Class<?> c = Class.forName(BASE + kind + "Plugin");                        // FLAGGED
loader.loadClass(String.format("com.acme.codec.%sCodec", format));         // FLAGGED
String renderer = req.getParameter("renderer");
Object r = Class.forName(renderer).getDeclaredConstructor().newInstance(); // FLAGGED
```

Not flagged: `Class.forName("org.postgresql.Driver")`, `Class.forName(DRIVER_CLASS)`, a lookup after `if (!ALLOWED.contains(kind)) throw ...`.

## Remediation

1. Map the input to a fixed set of `Class` objects (a `Map<String, Class<?>>` or an enum) instead of building a class name.
2. If a dynamic name is unavoidable, check it against an explicit allow-list before loading it.
