## Overview

VNX-561 maps to [CWE-561: Dead Code](https://cwe.mitre.org/data/definitions/561.html). It reports statements that can never execute.

## Why this matters

Dead code is usually a mistake about order: the audit call, the cleanup or the log line was written after the `return`, so it never happens and nothing says so. A block behind `if (false)` is code that is still read, reviewed and maintained but never tested, and is one edit away from being switched back on.

## What gets flagged

```javascript
if (!user) {
  throw new Error('not signed in');
  audit('anonymous access');        // FLAGGED: never runs
}
```

```python
if user.is_admin:
    return True
    audit(user)                     # FLAGGED: never runs
```

```java
if (false) {                        // FLAGGED
    refundAll();
}
```

Not flagged: a closing brace, `else`/`elif`/`except`/`catch`/`finally`, a `case`/`default` label or a dedent after the exit; hoisted JavaScript function declarations after a `return`; multi-line return expressions; braceless `if` bodies; the generator idioms `return` then `yield` and `if False: yield`; `if False:` guarding type-only imports; named flags such as `if (DEBUG)` and `TYPE_CHECKING`; Java statements after an exit (javac rejects them); test files; comments, block comments, docstrings and string literals. Comparisons that are always false are reported by VNX-570.

## Remediation

1. Move the statement before the exit if it was meant to run, or delete it.
2. Delete `if (false)` blocks, or put the code behind a named configuration flag that is tested.

## Suppressing this rule

Put a `nosec` comment on the line, or on line 1 to cover the whole file. Use the comment marker of the file's language (`#`, `//`, `--` or `;`):

```text
# nosec vnx-561
// nosec vnx-561
```

Or record an ignore rule: `vulnetix ignore add --rule vnx-561 --reason "..."`. See [Suppressing findings](/sast/guides/suppressing-findings/).
