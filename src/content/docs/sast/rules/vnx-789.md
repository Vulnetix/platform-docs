## Overview

VNX-789 maps to [CWE-789: Memory Allocation with Excessive Size Value](https://cwe.mitre.org/data/definitions/789.html). It reports C and C++ allocations (`malloc`, `calloc`, `realloc`, `reallocarray`, `alloca`, `valloc`, `new T[n]`, and the container calls `v.resize(n)`, `v.reserve(n)` and `std::vector<T> v(n)`) whose size is an externally controlled number:

- a value parsed with `atoi`/`atol`/`strtol`/`strtoul`/`std::stoi` and friends
- a value read with `scanf`/`fscanf`/`sscanf`
- a length decoded from the wire with `ntohl`/`ntohs`/`be32toh`/`le32toh` and friends

The value must be assigned in the ten lines above the allocation (or the parse call written inline in the size argument). A comparison against an upper limit or a `MIN()`/`std::min` clamp between the read and the allocation suppresses the report; a lower-bound check such as `n < 0` alone does not. Sizes from `strlen()`, `sizeof` or constants, and flows across functions, are not reported.

## Why This Matters

The requester chooses how much memory the process allocates. A 4 GiB length prefix exhausts memory, `alloca()` with a large value runs past the stack guard page, and a size that wraps after arithmetic allocates a tiny buffer that a later copy overflows.

## What Gets Flagged

```c
int count = atoi(argv[1]);
char *buf = malloc(count * sizeof(char));    // FLAGGED

len = ntohl(raw);
payload = malloc(len);                       // FLAGGED
```

Not flagged:

```c
int count = atoi(argv[1]);
if (count <= 0 || count > MAX_COUNT)
    return NULL;
return malloc(count);
```

## Remediation

1. Reject sizes above a fixed maximum appropriate to the data before allocating.
2. Use `calloc`/`reallocarray` for counts times element sizes so the multiplication is overflow-checked.
3. Never pass input-derived sizes to `alloca()` or variable-length arrays.
