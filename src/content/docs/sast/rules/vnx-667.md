## Overview

VNX-667 maps to [CWE-667: Improper Locking](https://cwe.mitre.org/data/definitions/667.html). It reports two Java locking mistakes that compile, look correct and still fail:

1. **A shared monitor.** `synchronized` on a String literal, an `.intern()`ed string, `Boolean.TRUE`/`FALSE`, a `valueOf(...)` box, or a field, variable or method parameter the file declares as `String`, `Boolean`, `Integer`, `Long`, `Short`, `Byte` or `Character`. Interned strings and cached boxes are the same object everywhere in the JVM, so unrelated code (another library, another tenant) contends on, or deadlocks with, your lock. A boxed field reassigned inside the block (`generation++`) changes the monitor while it is held.
2. **A lock with no finally.** A statement `lock.lock()` or `lockInterruptibly()` (also `rw.readLock().lock()`) with no `finally` in the next 60 lines that calls the same receiver's `unlock()`. An exception in the critical section leaves the lock held forever.

## What Gets Flagged

```java
private static final String LOCK = "LOCK";
synchronized (LOCK) { n++; }                 // FLAGGED: interned literal
synchronized (tenant.intern()) { ... }        // FLAGGED
synchronized (Boolean.TRUE) { ... }           // FLAGGED
```

```java
lock.lock();                                  // FLAGGED: unlock() is skipped if this throws
if (amount > balance) throw new IllegalStateException();
balance -= amount;
lock.unlock();
```

## What Is Not Flagged

- `synchronized (this)`, `synchronized (Foo.class)`, or a private `Object` field.
- `lock.lock(); try { ... } finally { lock.unlock(); }`, and `try { lock.lock(); ... } finally { lock.unlock(); }`.
- `tryLock()`, `FileChannel.lock()` assignments, methods that are themselves named `lock`/`acquire` (wrappers).
- Test files (for the Lock shape), comments and string literals.

## Remediation

```java
private final Object lock = new Object();
synchronized (lock) { ... }

lock.lock();
try {
    ...
} finally {
    lock.unlock();
}
```
